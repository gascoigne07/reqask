# Вопросы по документу «requirements.md»

Вопросы собраны агентом проверки требований. Под каждым вопросом: что сейчас написано в документе, варианты ответа и что изменится при каждом из них. Достаточно ответить номером варианта или своим текстом.

## Вопросы заказчику (бизнес)

### Q-04. Какое правило верно для push: один push за месяц (Ф-3, строка 39) или push при каждом переходе через порог независимо от истории (Ф-4, строка 40)?

- Сейчас в документе: `На карту приходится максимум один такой push за календарный месяц.` (строка 39); `Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.` (строка 40); `Изменение порога сохраняет накопленные расходы.` (строка 126).
- Суть: Ф-3 ставит лимит один push в месяц, Ф-4 описывает повторный push после смены порога.
- Варианты:
  1. Один push за месяц, возврат и повтор не сбрасывают лимит. Последствие: Лимит по месяцу в логике и тестах, возврат не сбрасывает признак
  2. Push при каждом переходе через порог, лимит месяца снимается. Последствие: Убрать правило одного push за месяц из Ф-3
- Рекомендуем: вариант 1, потому что Ф-3 задаёт лимит явно, Ф-4 описывает только накопление суммы.
- Без ответа нельзя: Нельзя реализовать и протестировать отправку push по месяцам.

### Q-05. Какой момент определяет месяц покупки: дата совершения (Ф-2, строка 38) или дата проведения (критерий приёмки, строка 64)?

- Суть: Ф-2 задаёт дату совершения, критерий приёмки относит покупку по дате проведения.
- Варианты:
  1. Дата совершения покупки в Алматы. Последствие: Критерий строки 64 переписать под дату совершения покупки
  2. Дата проведения покупки. Последствие: Ф-2 переписать, отнесение к месяцу по дате проведения
- Рекомендуем: вариант 1, потому что совпадает с формулировкой правила Ф-2 в документе.
- Без ответа нельзя: Нельзя определить месяц покупки на границе месяца.

### Q-07. Какой срок от проведения покупки до push считается верным: сразу при покупке (строка 23) или не позже минуты (строка 46)?

- Сейчас в документе: `Дать клиенту возможность узнать о достижении личного бюджета в момент покупки.` (строка 23); `Сервис передаёт push на отправку в течение минуты после получения события.` (строка 46).
- Суть: Цель требует момента покупки, NFR допускает задержку до минуты.
- Варианты:
  1. Сразу при проведении покупки. Последствие: Заменить минуту на немедленную отправку, нагрузка выше
  2. Не позже минуты после проведения покупки. Последствие: Переписать цель строки 23 под задержку до минуты
- Без ответа нельзя: Нельзя проверить срок отправки push и нефункциональное требование.

### Q-12. Отправляется ли push при изменении порога, если накопленная сумма уже равна новому порогу или выше его (Ф-4, строка 40)?

- Сейчас в документе: `Если она ниже нового порога, следующее достижение вызывает push` (строка 40).

- Варианты:
  1. Нет, push только при следующем переходе через порог. Последствие: Добавить в Ф-4 явное правило для суммы не ниже порога
  2. Да, push сразу при сохранении порога. Последствие: Добавить правило немедленного push в Ф-4 и тесты
- Рекомендуем: вариант 1, потому что Ф-3 задаёт push только при переходе снизу вверх.
- Без ответа нельзя: Нельзя написать тест на изменение порога при уже достигнутой сумме.

## Вопросы аналитику

### Q-01. При отклонении суммы сервис отвечает кодом 400 или кодом 200 с result ERROR (строка 121)?

- Сейчас в документе: `При отклонении суммы вернуть прежнее состояние и результат ERROR.` (строка 121); `Ответ в случае, если параметры запроса заполнены неверно.` (строка 163); `{"result":"ERROR","message":"Проверьте сумму"}` (строка 171).
- Суть: Логика требует вернуть ERROR, а статус 400 описан для неверных параметров без уточнения.
- Варианты:
  1. 200 с result ERROR и полем message. Последствие: Статус 400 для суммы не используется, строка 163 переписать
  2. 400 с телом message. Последствие: Убрать пример ERROR с кодом 200 и правило строки 121
- Рекомендуем: вариант 2, потому что неверные параметры запроса по REST обычно отвечают кодом 400.
- Без ответа нельзя: Нельзя реализовать ответ при неверной сумме и проверку его кода.

- Рекомендуем: вариант 1, потому что хранение в тиынах исключает округление при переводе сумм.
