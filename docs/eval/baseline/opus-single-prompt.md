## 3. Проверка каждого требования

### ЦЕЛ-1 (стр. 23)
**Нарушены:** однозначность, проверяемость, осуществимость, непротиворечивость.

- **Z-01 · MAJOR · стр. 23.** Цитата: «Дать клиенту возможность узнать о достижении личного бюджета в момент покупки».
  «В момент покупки» нельзя проверить. Это противоречит НФТ-1 (стр. 46: «в течение минуты после получения события») и Ф-2 (стр. 38: учитываются «проведённые покупки»). Проведение (клиринг) обычно наступает через часы или дни после покупки.
  **Исправить:** «…узнать о достижении порога не позднее 60 с после получения системой события о покупке (тип события — см. Ф-2)».

### АРХ-1 (стр. 26)
**Нарушены:** полнота, согласованность с SEQ-1.

- **Z-02 · MINOR · стр. 26.** Цитата: «Мобильное приложение → сервис настроек. Карточный процессинг → учёт расходов → сервис push.»
  В схеме нет связи «учёт расходов → сервис настроек», хотя она есть в SEQ-1 (стр. 43). Нет и источника данных «сумма за месяц» для приложения.
  **Исправить:** добавить связь «учёт расходов → настройки» и связь «приложение → учёт расходов» (или «настройки → учёт расходов») для чтения суммы.

### UI-1 (стр. 29)
**Нарушены:** полнота, прослеживаемость, осуществимость.

- **Z-03 · MAJOR · стр. 29.** Цитата: «На экране видны переключатель, поле «Порог, ₸», сумма за месяц и кнопка «Сохранить».»
  Ни один метод части B не отдаёт ни сумму за месяц, ни текущие настройки. Экран в описанном виде реализовать нельзя.
  **Исправить:** описать метод чтения (например, `GET /cards/{cardId}/spending-alert` → `amount`, `enabled`, `monthSpent`, `month`) или убрать сумму с экрана.
- **Z-04 · MINOR · стр. 29.** Цитата: «При ошибке ввода сообщение появляется под полем.»
  Не перечислены случаи ошибок (пусто, не число, вне диапазона, дробное значение). Нет текстов сообщений. Не описано поведение поля при выключенном переключателе и экран для неактивной или не-KZT карты.
  **Исправить:** таблица «условие → текст сообщения → блокируется ли кнопка», связанная с API-Л3/Л5.

### BPMN-1 (стр. 34)
**Нарушены:** полнота.

- **Z-05 · MINOR · стр. 34.** Цитата: «Проведение покупки → пересчёт расходов → проверка порога → при достижении отправка push → завершение.»
  Нет ветвлений: уведомление выключено, push в этом месяце уже был, операция исключённого типа, возврат, повторное событие.
  **Исправить:** добавить шлюзы для каждого из этих условий.

### Ф-1 (стр. 37)
**Нарушены:** полнота, атомарность.

- **Z-06 · MAJOR · стр. 37.** Цитата: «Держатель активной карты KZT задаёт целый порог…»
  Не определено поведение для неактивной (заблокированной, закрытой) карты и для карты не в KZT. Неясно, сохраняется ли настройка при блокировке и продолжается ли учёт. API (стр. 117–121) это условие не проверяет.
  **Исправить:** «Экран и метод сохранения доступны только для карт в статусе ACTIVE с валютой счёта KZT. Для прочих карт API возвращает <код>. При смене статуса карты уведомления <приостанавливаются / удаляются>».
- **Z-07 · MINOR · стр. 37.** Цитата: «По умолчанию уведомление выключено.»
  В одном пункте два требования: диапазон и значение по умолчанию. Значение порога по умолчанию не задано. Неясно, обязателен ли порог при `enabled=0` (в API `amount` обязателен всегда, стр. 143).
  **Исправить:** разделить на Ф-1.1 (диапазон) и Ф-1.2 (умолчания: `enabled=0`, `amount=null`), указать обязательность порога при выключении.

### Ф-2 (стр. 38)
**Нарушены:** непротиворечивость, однозначность, полнота, атомарность, корректность.

- **Z-08 · CRITICAL · стр. 38 и 64.** Цитаты: «Месяц определяется по дате совершения покупки в Алматы» (38) и «Покупка 31 января в 23:58 на 4 000 ₸ | Провести 1 февраля в 00:03 по Алматы | Февральский счётчик вырос на 4 000 ₸» (64).
  По Ф-2 покупка 31 января относится к январю. Критерий приёмки требует учесть её в феврале, то есть по дате проведения. Прямое противоречие: разработка и тестирование реализуют разные правила, а приёмочный тест заведомо не совпадёт с одним из них.
  **Исправить:** выбрать одну дату (совершения или проведения), исправить Ф-2 либо КП-2. Добавить в глоссарий термины «дата совершения» и «дата проведения» с указанием поля события процессинга.
- **Z-09 · MINOR · стр. 38.** Цитата: «…по дате совершения покупки в Алматы.»
  Часовой пояс не задан явно. С 01.03.2024 в Казахстане единый пояс UTC+5, ранее для Алматы действовал UTC+6. Велик риск «зашить» устаревшее смещение.
  **Исправить:** «граница месяца — 00:00 по времени Asia/Almaty (IANA tz)».
- **Z-10 · MAJOR · стр. 38.** Цитаты: «В расходы входят проведённые покупки.» «Переводы и снятие наличных исключаются.»
  Классификация операций неполная. Не сказано, как учитывать оплату услуг, комиссии, квази-кэш, платежи в приложении, отмены авторизаций и реверсы. Валютные покупки не описаны: по какому курсу и в какой момент они пересчитываются в KZT. Термин «проведённая» не определён.
  **Исправить:** таблица «тип операции / MCC → учитывается / не учитывается / уменьшает» и правило конвертации.
- **Z-11 · MAJOR · стр. 38.** Цитата: «Возврат уменьшает расходы месяца исходной покупки.»
  Не определено:
  - возврат в другом месяце: меняется ли закрытый месяц и что видит клиент;
  - частичный возврат;
  - возврат без ссылки на исходную операцию;
  - влияние на признак отправки push.

  Кроме того, Ф-2 объединяет четыре самостоятельных правила.
  **Исправить:** разбить Ф-2 на Ф-2.1–Ф-2.4 и для возвратов описать перечисленные случаи. Указать ключ связи с исходной операцией (см. ДАН-1).

### Ф-3 (стр. 39)
**Нарушены:** непротиворечивость, проверяемость, осуществимость, полнота.

- **Z-12 · CRITICAL · стр. 39 и 40.** Цитаты: «На карту приходится максимум один такой push за календарный месяц» (39) и «следующее достижение вызывает push независимо от истории предыдущей настройки» (40).
  Пример: push уже отправлен, клиент поднял порог, расходы снова его достигли. По Ф-4 нужен второй push, по Ф-3 он запрещён. Признак отправки (стр. 49) не может одновременно учитывать историю и игнорировать её.
  **Исправить:** явно выбрать правило. Вариант: «Признак отправки сбрасывается при сохранении нового порога. Ограничение — не более одного push на одно значение порога в месяц». Второй вариант — запретить повторный push и удалить фразу «независимо от истории» из Ф-4.
- **Z-13 · MAJOR · стр. 39.** Цитата: «…клиент получает push.»
  Доставка на устройство зависит от APNs/FCM и настроек ОС, поэтому требование непроверяемо в зоне ответственности системы. Не описаны случаи:
  - переход через порог при выключенном уведомлении, затем включение;
  - позднее проведение январской покупки уже в феврале: отправлять ли push «за январь».

  **Исправить:** «Сервис расходов передаёт запрос в сервис push…». Добавить правила для обоих случаев.
- **Z-14 · MINOR · стр. 39.** Цитата: «за календарный месяц».
  Не указано, что месяц определяется так же, как в Ф-2: по той же дате и в том же часовом поясе.
  **Исправить:** «за месяц учёта по Ф-2».

### Ф-4 (стр. 40)
**Нарушены:** полнота, однозначность.

- **Z-15 · MAJOR · стр. 40.** Цитата: «Если она ниже нового порога, следующее достижение вызывает push…»
  Не описан случай, когда новый порог меньше или равен накопленной сумме: push сразу, при следующей покупке или не отправляется вовсе. Буквальное применение Ф-3 означает «никогда в этом месяце». Неясно, считается ли «изменением порога» включение и выключение переключателя. Формулировка «история предыдущей настройки» размыта.
  **Исправить:** таблица переходов (старый порог, новый порог, накопленная сумма, признак отправки) → действие.

### SEQ-1 (стр. 43)
**Нарушены:** однозначность, полнота.

- **Z-16 · MAJOR · стр. 43.** Цитата: «передать последние четыре цифры карты и сумму при достижении порога.»
  «Сумма» может означать сумму покупки, накопленную сумму или порог. Текст push и локализация не заданы. В диаграмме нет проверок флага `enabled` и признака отправки, нет записи признака и нет обработки ошибки сервиса push (повтор, таймаут).
  **Исправить:** указать поля контракта (`maskedPan`, `monthSpent`, `threshold`), шаблон текста RU/KZ и шаги «проверить enabled → проверить признак → отправить → записать признак», а также политику повторов.

### НФТ-1 (стр. 46)
**Нарушены:** проверяемость, однозначность.

- **Z-17 · MAJOR · стр. 46.** Цитата: «Сервис передаёт push на отправку в течение минуты после получения события.»
  Не заданы перцентиль (p95 или p99), точки замера (вход в сервис расходов или запись в очередь push) и нагрузка, при которой норма должна выполняться. Неясно, о каком «событии» идёт речь: авторизации или проведения.
  **Исправить:** «p99 ≤ 60 с от получения события проведения сервисом расходов до приёма запроса сервисом push при нагрузке N событий/с».

### ДАН-1 (стр. 49)
**Нарушены:** непротиворечивость, полнота.

- **Z-18 · MAJOR · стр. 49.** Цитата: «…сумму покупки в тиынах, признак отправки и порог в тенге.»
  Сумма хранится в тиынах, порог в тенге, а сравниваются они между собой. Это источник ошибок округления и сравнения. В перечне нет:
  - флага `enabled` (хотя он есть в API как поле БД, стр. 144);
  - типа операции;
  - даты и времени операции;
  - ссылки на исходную операцию для возврата;
  - накопленной суммы;
  - срока хранения.

  **Исправить:** единая единица (тиыны) для всех сумм, полная логическая модель с ключами (`card_id + month`, `operation_id` уникален) и сроком хранения.

### ИНТ-1 (стр. 52)
**Нарушены:** непротиворечивость, полнота, прослеживаемость.

- **Z-19 · CRITICAL · стр. 52 и 103.** Цитаты: «Приложение читает и сохраняет настройки через дочерний документ…» (52) и «Сохранение порога. Функциональные требования: чтение порога» (103).
  Часть B описывает один метод `saveLimit`. Метода чтения нет, поэтому экран UI-1 нельзя отобразить: нет ни текущего порога, ни флага, ни суммы за месяц.
  **Исправить:** добавить в часть B метод чтения настроек и суммы за месяц с полной спецификацией.

### ИНТ-2 (стр. 52)
**Нарушены:** однозначность, полнота, атомарность.

- **Z-20 · MAJOR · стр. 52.** Цитата: «Повторная доставка одного события процессинга сохраняет исходный итог.»
  Не задан ключ идемпотентности (вероятно, `идентификатор операции` из стр. 49). Не уточнено, что «итог» включает и сумму, и признак push, то есть повторного push быть не должно. Сама интеграция с процессингом не специфицирована: транспорт, формат события, типы событий (проведение, возврат, реверс), гарантии доставки и порядок.
  **Исправить:** отдельный раздел «Контракт события процессинга» и формулировка «повторное событие с тем же `operation_id` не изменяет сумму и не порождает push».

### ТСТ-1 (стр. 57)
- **Z-21 · MINOR · стр. 57.** Цитата: «заполняются тестировщиками».
  Раздел пуст, нет тестовой стратегии и данных.
  **Исправить:** заполнить до старта или зафиксировать срок и ответственного.

### КП-1 (стр. 63)
- **Z-22 · MINOR · стр. 63.** Цитата: «Расходы 48 500 ₸, порог 50 000 ₸».
  Неполные исходные условия: не сказано, что уведомление включено, карта активна и в KZT, push в этом месяце не отправлялся. Без этого результат «один push» не определён.
  **Исправить:** дополнить предусловия.

### КП-2 (стр. 64)
- (противоречие с Ф-2 — см. **Z-08**).
- **Z-23 · MINOR · стр. 64.** Цитата: «Покупка 31 января в 23:58».
  Часовой пояс времени покупки не указан, тогда как для проведения он указан. Ожидаемый результат зависит от пояса.
  **Исправить:** «31 января 23:58 по Asia/Almaty».

### КП-3 (стр. 65)
- **Z-24 · MINOR · стр. 65.** Цитата: «Счётчик показывает 19 900 ₸».
  Не проверяется отсутствие push. Не указано, где именно смотреть «счётчик»: в UI, в API или в БД.
  **Исправить:** «счётчик в ответе метода чтения = 19 900 ₸, push не отправлен».

### API-ОБЩ (стр. 103–114)
**Нарушены:** непротиворечивость, корректность, полнота.

- **Z-25 · MAJOR · стр. 103.** Цитата: «Сохранение порога. Функциональные требования: чтение порога».
  Назначение метода противоречит само себе.
  **Исправить:** «Сохранение настройки уведомления о пороге (Ф-1, Ф-4)».
- **Z-26 · MAJOR · стр. 104, 109.** Цитата: «GET».
  Метод меняет состояние, а GET по RFC 9110 должен быть безопасным и идемпотентным. Отсюда риски: кэширование прокси, предзагрузка, CSRF, а также попадание `cardId` и суммы в журналы URL.
  **Исправить:** `PUT /cards/{cardId}/spending-alert` с JSON-телом `{amount, enabled}`.
- **Z-27 · MAJOR · стр. 108, 110.** Цитаты: «Prod: —», «Swagger | —».

## 4. Проверка набора требований целиком

**Противоречия:**
- Ф-2 ↔ КП-2: дата отнесения к месяцу (Z-08).
- Ф-3 ↔ Ф-4: лимит push (Z-12).
- ИНТ-1 ↔ часть B: чтение настроек (Z-19).
- API-Л5 ↔ статусы 400 и 200: обработка ошибки (Z-30).
- 403 ↔ 404 (Z-37).
- Тиыны ↔ тенге (Z-18).
- Описание ↔ метод GET (Z-25, Z-26).

**Дубли:** Ф-1 ↔ API-П1 ↔ стр. 143; Ф-4 ↔ API-П3 (Z-43).

- **Z-38 · MAJOR · стр. 23, 38, 46.** Цитаты: «в момент покупки», «В расходы входят проведённые покупки», «в течение минуты после получения события».
  Цепочка времени неосуществима как единое целое. Цель требует реакции на покупку, учёт ведётся по проведению, а НФТ отсчитывается от неопределённого «события». Покупка, проведённая после конца месяца, может породить push «за прошлый месяц».
  **Исправить:** зафиксировать триггер (авторизация или проведение), согласовать с ним цель и НФТ, описать поведение для поздних проведений.
- **Z-39 · MAJOR · стр. 68, 72–85, 91.** Цитаты: «Документ (версия/дата) в источнике не заполнен», «отметки не проставлены», «| | | |».
  Нет версии и согласований, чек-лист не заполнен. У НФТ, данных, интеграции и UI нет идентификаторов, критерии приёмки не ссылаются на Ф-x. Это нарушает прослеживаемость (29148, 5.2.5 Traceable) и модифицируемость (IEEE 830, 4.3.7).
  **Исправить:** присвоить ID всем требованиям, добавить колонку «Требование» в критерии приёмки, заполнить версию, чек-лист и согласующих.
- **Z-40 · MAJOR · стр. 61–65.** Цитата: таблица из трёх критериев.
  Покрытие неполное. Нет критериев для:
  - границ 999 / 1 000 / 1 000 000 / 1 000 001;
  - умолчания «выключено»;
  - возврата;
  - Ф-4;
  - второго пересечения в месяце;
  - идемпотентности;
  - НФТ-1;
  - кодов ошибок API.

  **Исправить:** минимум один позитивный и один негативный критерий на каждое требование.
- **Z-41 · MAJOR · стр. 45–46, 82.** Цитата: «Структура требований не несёт изменений и рисков информационной безопасности».
  Нет НФТ по доступности, пропускной способности, мониторингу и журналированию, сроку хранения данных и ИБ: маскирование PAN в push и логах, параметры в URL, защита от перебора `cardId`.
  **Исправить:** раздел НФТ с измеримыми значениями и заключение ИБ.
- **Z-42 · MAJOR · весь документ.** Пробел (цитаты нет, требование отсутствует).
  Не описан жизненный цикл: перевыпуск карты (новый `cardId`), блокировка и закрытие, несколько карт на одном счёте, отключённые push в ОС, смена устройства, язык push.
  **Исправить:** раздел «Особые случаи» с правилами для каждого.
- **Z-43 · MINOR · стр. 37/124/143; 40/126.** Дубли правил диапазона и сохранения накоплений. Это риск расхождения при правке.
  **Исправить:** держать правило в одном месте, в остальных местах давать ссылку.
- **Z-44 · MINOR · весь документ.** Нет глоссария для терминов «проведённая покупка», «возврат», «итог», «событие», «месяц учёта», «тиын».

## Вопросы автору документа

1. **По какой дате операция относится к месяцу (Ф-2 против КП-2)?**
   - а) По дате совершения (авторизации). Исправляется КП-2. Поздние проведения попадают в уже закрытый месяц, нужно правило для push «за прошлый месяц».
   - б) По дате проведения. Исправляется Ф-2. Реализация проще, но расходы в приложении расходятся с датами чеков клиента.

2. **Допустим ли второй push в месяце после изменения порога (Ф-3 против Ф-4)?**
   - а) Нет. Из Ф-4 удаляется «независимо от истории». Клиент, поднявший порог, о новом пороге не узнает.
   - б) Да, признак сбрасывается при каждом сохранении порога. Нужно ограничение от злоупотреблений, Ф-3 переформулируется.
   - в) Да, но не более N push в месяц. Компромисс, нужен счётчик вместо признака.

3. **Что делать, если новый порог меньше или равен уже накопленной сумме?**
   - а) Сразу отправить push. Нужен вызов сервиса push из сценария сохранения настроек.
   - б) Отправить при следующей покупке. Это отступление от правила «перехода» в Ф-3, его нужно явно зафиксировать.
   - в) Не отправлять в этом месяце. Проще всего, но клиент может не понять, почему уведомления нет.

4. **Что делать, если порог пересечён при выключенном уведомлении, а затем уведомление включено?**
   - а) Push не отправляется, признак не ставится. Возможен «тихий» месяц.
   - б) Push при включении. Понадобится проверка в API сохранения.

5. **Что является триггером уведомления: авторизация или проведение?**
   - а) Авторизация. Близко к цели «в момент покупки», но нужно обрабатывать отмены авторизаций и расхождение сумм с проведением.
   - б) Проведение. Надёжнее, но задержка составляет часы или дни, и цель (стр. 23) нужно переформулировать.

6. **Какие операции входят в «покупки»?**
   - а) Только POS и e-commerce с исключением квази-кэш MCC. Точнее отражает «бюджет», нужен справочник MCC.
   - б) Все дебетовые, кроме переводов и снятия наличных. Проще, но в расходы попадут комиссии и платежи.

7. **Как учитывать покупки в иностранной валюте?**
   - а) Сумма в KZT по курсу авторизации. Совпадает с тем, что клиент видит сразу.
   - б) Сумма списания по проведению. Точнее, но сумма может измениться задним числом.
   - в) Исключать. Проще всего, но бюджет занижается.

8. **Как обрабатывать возвраты в другом месяце, частичные и без ссылки на исходную операцию?**
   - а) Уменьшать месяц исходной покупки, а возвраты без ссылки игнорировать. Нужна связь `original_operation_id`, закрытые месяцы меняются.
   - б) Уменьшать месяц возврата. Проще, но это противоречит текущей Ф-2.

9. **Откуда приложение берёт текущие настройки и сумму за месяц?**
   - а) Новый GET-метод в части B. Полнота достигается, но объём API растёт.
   - б) Отдельный API сервиса расходов. Ответственность разделена правильнее, но нужен второй документ.
   - в) Сумма с экрана убирается. Требования UI сокращаются, ценность функции снижается.

10. **Можно ли заменить GET на PUT или POST с JSON-телом?**
    - а) PUT `/cards/{cardId}/spending-alert`. Соответствует HTTP-семантике, нужна правка cURL и раздела тела запроса.
    - б) POST. Тоже допустимо, идемпотентность обеспечивается отдельно.
    - в) Оставить GET. Нужно принять риски кэширования, CSRF и логирования и получить письменное согласие ИБ.

11. **Какой ответ вернуть при недопустимой сумме?**
    - а) HTTP 400 + `result=ERROR` + код ошибки. Стандартно, клиент различает ошибки по коду.
    - б) HTTP 200 + `result=ERROR`. Тогда правило на стр. 151 придётся переписать, а мониторинг ошибок по HTTP-кодам станет слепым.

12. **Какой код вернуть для чужой карты?**
    - а) 404, как для отсутствующей. Не раскрывает факт существования карты, но 403 тогда нужно удалить из спецификации.
    - б) 403. Проще в диагностике, но позволяет перебором проверять существование карт.

13. **Что содержит push?**
    - а) Накопленную сумму и порог. Информативно, нужен шаблон и решение ИБ о составе данных.
    - б) Сумму последней покупки. Это не отвечает цели «достижение бюджета».
    - в) Только факт достижения порога. Минимум данных, ниже ценность.

14. **Как ведёт себя функция для неактивной или не-KZT карты?**
    - а) Экран скрыт, API отказывает с отдельным кодом. Нужны код ошибки и правило UI.
    - б) Настройка сохраняется, но учёт приостанавливается. Требует правил возобновления.
    - в) Настройки удаляются при блокировке. Проще, но клиент теряет настройку.

15. **Что происходит с настройкой и накоплениями при перевыпуске карты?**
    - а) Переносятся на новую карту. Нужна связь старого и нового `cardId` от процессинга.
    - б) Сбрасываются, уведомление снова выключено по умолчанию. Проще, но ухудшает клиентский опыт и требует информирования клиента.
